================================================================================
p2p-netcat-go-wrk — EXAMPLES
================================================================================
Четыре примера, каждый — свой "алгоритм" (тип сессии). Первые три — через
одиночный CLI-режим (для понимания механики), четвёртый — то, ради чего
всё затевалось: один мультитуннельный демон с несколькими алгоритмами
одновременно. Все PeerId ниже — примерные, у вас будут свои (см. `p2p-nc id`).

================================================================================
Пример 1 — TCP forward (классический проброс порта, как ssh -L)
================================================================================
Задача: с ноутбука достучаться до PostgreSQL, который слушает только на
127.0.0.1 удалённой машины.

  На удалённой машине (там, где Postgres):
    $ p2p-nc id
    12D3KooWRemoteMachineExamplePeerID...

    $ p2p-nc -l 15432 -d 127.0.0.1 -p 5432
    # слушает логический порт 15432, форвардит входящий поток на 127.0.0.1:5432

  На ноутбуке:
    $ p2p-nc 12D3KooWRemoteMachineExamplePeerID 15432 -p 15432
    # локальный listener на 127.0.0.1:15432, всё что туда прилетает —
    # уходит через p2p-туннель на удалённый Postgres

    $ psql -h 127.0.0.1 -p 15432 -U myuser mydb
    # работает так, будто Postgres локальный

Алгоритм: raw byte-forward, TCP-в-TCP, без парсинга протокола внутри
туннеля — Postgres ничего не знает про p2p, просто видит входящее TCP-
соединение "как будто с localhost".

================================================================================
Пример 2 — SOCKS5 exit-node (единая точка выхода в интернет)
================================================================================
Задача: превратить удалённую машину (скажем, VPS в другой стране) в
SOCKS5-прокси, доступный только через p2p, без открытого порта наружу.

  На VPS (exit-node):
    $ p2p-nc -l 10800 -S --pairing-token-file ~/.config/p2p-netcat/socks.token
    # -S = поднять SOCKS4/4a/5-сервер на логическом порту 10800;
    # без --allow-unauthenticated-listener обязателен pairing-токен

  На клиентской машине:
    $ p2p-nc VPS_PEER_ID 10800 -p 1080 --pairing-token-file ~/.config/p2p-netcat/socks.token
    # локальный SOCKS5-прокси на 127.0.0.1:1080

    $ curl --socks5 127.0.0.1:1080 https://ifconfig.me
    # вернёт IP-адрес VPS, а не клиентской машины

Алгоритм: SOCKS5-негоциация (CONNECT/BIND) происходит НА СТОРОНЕ СЕРВЕРА
(session.SOCKS парсит запрос уже после того, как байты прошли через
туннель) — клиент просто гоняет сырые байты, как в Примере 1. Разница с
Примером 1 не в транспорте, а в том, что сервер сам решает, куда
законнектиться, по каждому SOCKS-запросу отдельно, а не форвардит на
фиксированный target.

================================================================================
Пример 3 — Исходящий трафик узла через SOCKS/Tor (upstream_socks)
================================================================================
Задача: сам p2p-nc узел должен выходить в сеть не напрямую, а через Tor
(или любой другой SOCKS5-прокси) — то есть скрыть собственный IP узла от
relay-серверов и DHT, а не только проксировать чужой трафик, как в
Примере 2.

  Запуск Tor локально (отдельная задача, вне scope p2p-netcat) — допустим
  слушает 127.0.0.1:9050, как обычно.

    $ p2p-nc -l 8080 -d 127.0.0.1 -p 80 --upstream-socks 127.0.0.1:9050
    # ВНИМАНИЕ: при --upstream-socks узел автоматически отключает QUIC,
    # WebRTC и обычный WebSocket-транспорт (они физически не проксируются
    # через SOCKS5 в текущей версии) — остаётся только TCP-транспорт.
    # Это защита от утечки мимо прокси, не баг.

Алгоритм: тот же TCP forward, что и в Примере 1, но с другим dialer'ом на
уровне libp2p-транспорта — каждое исходящее TCP-соединение узла (к relay,
к пирам) идёт через SOCKS5 CONNECT к 127.0.0.1:9050 вместо прямого
net.Dial. См. p2p.Config.UpstreamSOCKS / internal/daemon upstream_socks
в конфиге — работает одинаково что в одиночном режиме, что в демоне.

================================================================================
Пример 4 — Мультитуннельный демон: всё вместе + hot-reload
================================================================================
Задача: одна конфигурация, поднимающая Postgres-forward (Пример 1) И
SOCKS5 exit-node (Пример 2) одновременно, в одном процессе, с исходящим
трафиком узла через Tor (Пример 3) — то, ради чего строился Эпик 1.

  ~/.config/p2p-netcat/tunnels.yaml:
  --------------------------------------------------------------------------
  identity: ~/.config/p2p-netcat/identity.key
  upstream_socks: 127.0.0.1:9050

  tunnels:
    - name: postgres
      type: forward
      mode: server
      protocol: tcp
      logical_port: 15432
      target: 127.0.0.1:5432
      token_file: ~/.config/p2p-netcat/tokens/postgres.token

    - name: exit-proxy
      type: socks
      mode: server
      logical_port: 10800
      token_file: ~/.config/p2p-netcat/tokens/socks.token
  --------------------------------------------------------------------------

    $ p2p-nc run --config ~/.config/p2p-netcat/tunnels.yaml
    [p2p-ncd] PeerId: 12D3KooW...
    [p2p-ncd] 2 tunnel(s) running; Ctrl+C to stop
    [p2p-ncd] tunnel postgres: listening on logical port 15432 (forward/tcp)
    [p2p-ncd] tunnel exit-proxy: listening on logical port 10800 (socks/tcp)

  Дальше можно дописать в YAML третий туннель (скажем, admin-shell типа
  pty) и просто СОХРАНИТЬ ФАЙЛ — процесс НЕ нужно перезапускать:

    [p2p-ncd] config reloaded from /home/user/.config/p2p-netcat/tunnels.yaml
    [p2p-ncd] tunnel admin-shell: listening on logical port 2222 (pty/tcp)

  (по умолчанию файл проверяется на изменения раз в 2 секунды,
  --watch-interval 0 отключает автоперезагрузку)

Алгоритм: один libp2p.Host на весь процесс, каждый туннель — это просто
ещё один SetStreamHandler на том же Host'е (см. internal/daemon). Все три
"алгоритма" из примеров 1-3 сосуществуют на одном PeerId одновременно —
собственно это и решало исходную проблему "один процесс = один порт".
